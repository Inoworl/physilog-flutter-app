# PhysiLog - 実装計画概要

## プロジェクト概要

**PhysiLog** は、スポーツ体力測定の動画を活用した計測アプリである。
ユーザーが撮影した動画を取り込み、フレーム単位で再生位置を操作しながら、タイムや距離などの計測値を記録・管理できる。

### 想定ユーザー
- 体育教員、スポーツコーチ、部活動顧問
- 体力テストの記録を効率化したい学校関係者

### 解決する課題
- 体力測定時のストップウォッチ操作と記録の同時作業が困難
- 動画で撮影しておけば、後から正確にタイムを計測できる
- 複数人の記録を一括管理できる

## 技術スタック選定

| カテゴリ | 推奨技術 | 代替候補 |
|---------|---------|---------|
| フレームワーク | **Flutter** | React Native |
| 言語 | **Dart** (Flutter) | TypeScript (React Native) |
| バックエンド | **Firebase** (Firestore, Auth, Storage) | - |
| 状態管理 | **Riverpod** | Provider, BLoC |
| 動画操作 | **video_player** + **ffmpeg_kit_flutter** | chewie |
| ローカルDB | **Hive** or **Isar** | sqflite |

### Flutter を推奨する理由

1. **クロスプラットフォーム**: iOS / Android を単一コードベースで開発可能
2. **動画操作ライブラリが豊富**: `video_player`、`ffmpeg_kit_flutter` などフレーム単位操作に必要なライブラリが充実
3. **パフォーマンス**: ネイティブコンパイルによる高いレンダリング性能。動画再生とUI操作の同時処理に有利
4. **Dart 言語**: 型安全で学習コストが低く、非同期処理が書きやすい

### React Native（代替候補）の評価

- JavaScript/TypeScript エコシステムの活用が可能
- ただし、動画のフレーム単位操作においてはネイティブブリッジの制約がある
- 動画操作系ライブラリの成熟度が Flutter に比べやや劣る

## MVP 方針決定

### 動画保存方針

| 方針 | 内容 | メリット | デメリット |
|-----|------|---------|-----------|
| **方針A（推奨）** | 端末内のみに保存 | 実装がシンプル、通信不要、プライバシー保護 | 端末紛失時にデータ喪失 |
| 方針B | Firebase Storage にアップロード | バックアップ、端末間共有 | 通信コスト大、ストレージ費用、アップロード時間 |

**推奨: 方針A（端末内のみ）**

理由:
- MVP では機能検証が最優先であり、動画アップロード機能は複雑さを増す
- 体力測定動画は容量が大きく、クラウドストレージのコストが懸念される
- プライバシーの観点からも、生徒の映像を端末外に出さない方が安全
- 将来的にクラウドバックアップを追加する余地は残す

### 認証方針

| 方針 | 内容 | メリット | デメリット |
|-----|------|---------|-----------|
| 方針A | 認証なし | 最もシンプル | 将来のデータ同期が困難 |
| **方針B（推奨）** | Firebase 匿名ログイン | 導入コスト低、後から正規認証に昇格可能 | Firebase 依存 |
| 方針C | メール/パスワード認証 | セキュリティ高 | MVP にはオーバースペック |

**推奨: 方針B（Firebase 匿名ログイン）**

理由:
- ユーザーにアカウント作成の手間を掛けさせず、即座に使い始められる
- Firebase のユーザー ID が付与されるため、将来的なデータ同期やアカウント昇格に対応可能
- 実装コストが極めて低い（数行のコードで完了）

## 実装フェーズ

### Phase 1: プロジェクトセットアップ + データモデル

**期間目安**: 1〜2日

- Flutter プロジェクト作成・初期設定
- ディレクトリ構成の確立
- 依存パッケージの導入
- Firebase プロジェクトのセットアップ
- データモデルの定義（計測記録、動画メタデータ等）
- Riverpod の基盤セットアップ
- ルーティング設定

**成果物**: ビルド可能なプロジェクト骨格、データモデル定義

### Phase 2: 動画取り込み + 計測機能（コア機能）

**期間目安**: 3〜5日

- 動画ファイルの取り込み（カメラロールからの選択）
- 動画プレーヤーの実装（再生/一時停止/シーク）
- フレーム単位の再生位置操作
- 計測開始/終了のマーキング機能
- タイム計算ロジック（フレーム位置 → 時間変換）
- 計測結果のローカル保存

**成果物**: 動画を取り込み、フレーム操作で計測できる基本機能

### Phase 3: 記録管理（CRUD + 一覧表示）

**期間目安**: 2〜3日

- 記録一覧画面の実装
- 記録の詳細表示
- 記録の編集・削除機能
- 検索・フィルタリング（種目別、日付別）
- ローカルDBへのCRUD操作の完成

**成果物**: 記録の作成・閲覧・更新・削除が可能な管理画面

### Phase 4: 仕上げ（UI磨き込み、エラーハンドリング、テスト）

**期間目安**: 2〜3日

- UI/UX の磨き込み（アニメーション、レスポンシブ対応）
- エラーハンドリングの強化（動画読み込み失敗、ストレージ不足等）
- ユニットテスト・ウィジェットテストの作成
- パフォーマンス最適化（大容量動画への対応）
- リリース準備（アイコン、スプラッシュスクリーン等）

**成果物**: MVP としてリリース可能な品質のアプリ

## リスクと対策

### 1. 可変フレームレート（VFR）問題

**リスク**: スマートフォンで撮影された動画は可変フレームレート（VFR）であることが多く、フレーム位置と実時間の対応が不正確になる可能性がある。

**対策**:
- `ffmpeg_kit_flutter` を使用して動画メタデータ（フレームレート情報）を正確に取得する
- 必要に応じて、取り込み時に固定フレームレート（CFR）へトランスコードする
- ユーザーに対して「計測精度は動画のフレームレートに依存する」旨を明示する

### 2. 動画ストレージ容量

**リスク**: 体力測定動画は1本あたり数百MBになることがあり、端末のストレージを圧迫する。

**対策**:
- 動画のオリジナルファイルはカメラロールに残し、アプリ内では参照（パス）のみ保持する方式を検討
- 必要に応じて計測に必要な区間のみをトリミングして保存するオプションを提供
- ストレージ使用量の表示機能を将来的に追加

### 3. パフォーマンス

**リスク**: 高解像度（4K）動画のフレーム単位操作は、端末のスペックによっては動作が重くなる。

**対策**:
- 動画再生にはハードウェアデコーダを活用する（`video_player` のデフォルト挙動）
- サムネイル生成やフレーム抽出は非同期処理で行い、UI スレッドをブロックしない
- 必要に応じて再生解像度を下げるオプションを提供

### 4. プラットフォーム固有の制約

**リスク**: iOS と Android で動画コーデックのサポート状況やファイルアクセス権限が異なる。

**対策**:
- `permission_handler` パッケージでプラットフォーム別の権限管理を統一的に扱う
- 対応コーデック（H.264, H.265）の範囲を明確にし、非対応形式は取り込み時にエラー表示する
- プラットフォーム別の結合テストを実施する

### 5. データ喪失

**リスク**: 端末故障やアプリ削除により計測データが失われる。

**対策**:
- MVP では端末内保存を前提とするが、将来的にエクスポート機能（CSV, JSON）を追加する
- アプリ削除時の警告メッセージを表示する
- Phase 2 以降でクラウドバックアップオプションを検討する
